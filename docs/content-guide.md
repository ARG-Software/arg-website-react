# Content guide: blog posts and pattern pages

One place for every rule that applies when writing or editing content in `src/frontend/content/`. Folder paths are in `src/frontend/data/contentPaths.json`.

- Blog posts: `src/frontend/content/blog/{slug}.md`, served at `/blog/{slug}/`
- Pattern pages: `src/frontend/content/patterns/{slug}.md`, served at `/patterns/{slug}/`

Sitemap, RSS, Atom and prerendered HTML are generated by the build. Do not edit them by hand.

---

## 1. Blog post frontmatter

```yaml
---
seoTitle: Primary keyword first, 60 characters or less
slug: my-post-slug
author: José Antunes
authorUrl: https://www.linkedin.com/in/...
authorType: Person
authorSameAs: https://www.linkedin.com/in/...
tag: Architecture
tags: Architecture, Backend, Refactoring
title: Full article title
subtitle: Meta description. Primary keyword plus one secondary keyword.
intro: Usually the same text as subtitle
date: February 23, 2026
dateModified: February 23, 2026
reviewedOn: February 23, 2026
readTime: 10 min read
mediumUrl: https://medium.com/...
---
```

- `slug` never changes after publishing: it is the URL.
- `dateModified` is for SEO. `reviewedOn` is the date shown in the article header. `reviewedOn` requires `dateModified`, and `dateModified` can't be earlier than `date` (`npm run check:content` enforces both).
- Dates use the `Month D, YYYY` format.

## 2. Writing rules

- **Keywords must match the content.** A tech, version or comparison may go in `seoTitle`, `subtitle`, H2s or the FAQ only if the article body covers it. If it's missing, add a short, factual section first, then use the keyword.
- **Pick the keyword formula:** pattern + library/tool + problem/trend (licence change, alternative, "vs", error message). Check that people actually search the phrase before using it.
- **FAQ.** End with `## FAQ` and 3–4 questions phrased the way people search them. Write each as `- **Question?** Answer.` Answers only summarise what the article already says.
- **Internal links.** Add 2–3 links to related ARG posts or patterns, as `[text](/blog/{slug}/)`.
- **No double hyphens or emojis in prose** (`check:content` fails on them).
- **Inline formatting:** `**bold**`, `` `code` ``, and `[text](url)`. Raw HTML is not rendered.

## 3. Sources

- **Factual claims need a source**: versions, licences, limits, benchmarks, release dates. Use the primary source (official docs, release notes, the licence text), not a blog that repeats it.
- **Where to put them:** list them at the end, after the FAQ, under `## Sources`:

  ```markdown
  ## Sources

  - [Microsoft: Compare types related to date and time](https://learn.microsoft.com/...)
  - [MediatR: License](https://...)
  ```

  Format each entry as `Publisher: Page title`. Older posts use `## References` or `## Sources reviewed`. Use `## Sources` for new posts.
- **Keep links to ARG-owned companion repositories** (for example `https://github.com/ARG-Software/Clean-Architecture`), and keep article-specific citations that support a claim.
- **Don't add generic product homepages** (Node.js, TypeScript, React…) unless they are the actual citation.
- **No Medium promotion:** no Medium signup, byline, publication or promo links.
- **External URLs used by components** go through `src/frontend/data/siteLinks.json` and `linksService.js`. Links inside article Markdown are written inline.

## 4. Cover image

Website covers are **2560×1440 WebP**, at `/images/blog/.../{name}-header.webp`. Medium featured images are **PNG**, in `external/html/medium-updates/batch-3-vector-search/covers/{slug}.png`.

1. **Generate** `{slug}.png` at 16:9 with the prompt below.
2. **Convert** it to a 2560×1440 WebP (Squoosh, or `npx sharp-cli`). Save it under `public/images/blog/...`, and reference it as the first image of the post: `![descriptive alt](/images/blog/.../header.webp)`.
3. **Generate the smaller sizes** with `npm run blog:covers`. This writes the 480, 960 and 1600 sizes and updates `src/frontend/data/blogCoverSizes.json`.
4. **Write a descriptive alt:** describe the topic, not a poetic title. Run `npm run blog:check-images` to check it.
5. **For Medium,** copy the PNG to the Medium `covers/` folder and replace the story's featured image with it.

**ARG colours:** ink `#0c002e`, red `#f0060d`, magenta `#c924d7`, violet `#7904fd`, cream `#f4f1ea`.

**Image prompt** (paste one batch at a time; caption each image with the exact `FILENAME`):

```
Generate a SEPARATE image for EACH numbered item. Do not combine them.
Caption each image with the exact FILENAME (for Save As). Do NOT draw the filename on the artwork.

GLOBAL STYLE:
2560x1440, 16:9, Swiss / Bauhaus print poster: strong grid, flat geometry, bold type.
NOT architecture: no buildings, no floorplans, no compass, no columns, no city.
Software objects + logos only.
COLOR LOCK: large dark blue #0c002e field (~40%+), plus #f0060d #c924d7 #7904fd, cream #f4f1ea for small type only. No other hues.
No photoreal, no people, no laptops.
Logos and short tech words required, spelled correctly.
Each poster: different composition.

1. FILENAME: {slug}.png
   {topic line with required logos/words}
```

## 5. Pattern pages

Frontmatter:

```yaml
---
slug: cqrs
order: 1
title: CQRS Pattern
seoTitle: CQRS Pattern: C# and TypeScript Examples
subtitle: Meta description
category: Architecture        # one of the categories in src/frontend/data/patternsPage.json
tags: CQRS, .NET, TypeScript
relatedPosts: cqrs-without-mediatr, pragmatic-clean-architecture-aspnet-core
relatedPatterns: event-sourcing, aggregate
date: October 28, 2026
dateModified: October 28, 2026
---
```

- **Body order:**
  1. A one-sentence lead
  2. A short paragraph
  3. `## The problem`
  4. `## How it works`
  5. `## C# example`
  6. `## TypeScript example`
  7. `## When to use it`
  8. `## When to avoid it`
  9. `## FAQ`
- **Code examples are C# and TypeScript**, 20–40 lines each. Compile every snippet before publishing: C# with `dotnet build`, with no warnings; TypeScript with `tsc --noEmit` and `strict`.
- **Library names** (MassTransit, Polly, Temporal…) appear only where the page really covers them.

## 6. Linking posts and patterns

The pattern owns the link. To connect a post to a pattern, add the post's slug to the pattern's `relatedPosts`. Never edit the post for this.

- **The pattern page** lists the post under "Go deeper on the ARG blog".
- **The post** automatically shows a "Pattern reference: …" line at the end, both in the SPA and in the prerendered HTML.
- **Only add posts that treat the pattern in depth**, not posts that mention it in passing.
- **Bad slugs fail the build:** `npm run check:content` fails on an unknown slug in `relatedPosts` or `relatedPatterns`.

## 7. Before publishing

```bash
npm run check:content
npm run blog:check-images
npm run test:blog
npm run test:prerender
npm run build
```

Check `dist/blog/{slug}/index.html` (or `dist/patterns/{slug}/index.html`) for the `<title>`, the meta description, and the content.

## 8. After publishing

1. **Gaspar.** It reads Supabase, not the files, so ingest after the deploy: `npm run rag:ingest:local -- --file src/frontend/content/blog/{slug}.md` (or `.../patterns/{slug}.md`). `--all` is fine too, because unchanged sources are skipped by content hash. Run it with `--dry-run` first to see what will change. This writes to the production RAG tables. A pattern's `relatedPosts` also become Gaspar's article recommendations when that pattern is retrieved.
2. **Search Console.** Request indexing for the new or changed URL.
3. **Medium.** Updates are manual, and only after the website version is approved. For edits, prepare only the changed sections in `docs/medium-replacements/<batch>/`:
   - `{slug}.html`: paste-ready, with the links preserved
   - `{slug}.md`: the same content, for review
   - `{slug}.notes.md`: a checklist of the changed sections
4. **Other surfaces.** If the post changes company facts (services, pricing, projects), follow **Content Updates** in `README.md`, which covers `llms.txt`, JSON-LD and the prerender paragraphs.

Commits, pushes and PRs need explicit approval.
